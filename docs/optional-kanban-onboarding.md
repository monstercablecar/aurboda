# Optional Kanban onboarding

The existing Home setup guide remains the basic orientation and optional connection flow. Its final summary offers a brief handoff to the ordinary Tasks page (`/goals`). The deeper catalog lives in one **Onboarding** column, with no deadlines, reminders, required order or completion gate. A hidden Tasks page is explained through Settings → Feature Control instead of being automatically revealed. Existing dismissed/completed setup state is preserved; adding the column does not replay the guide.

Click a task title for its description and normal editing. Move by drag handle or ••• → Move to; use the checkmark or a Done-category column to complete. Each card can be edited, moved, archived or deleted using normal task behavior. Descriptions move with tasks. To remove the column, move or delete all its tasks, including archived tasks, then remove the empty column in Board settings. Deletion remains permanent under ordinary future logins, migrations and catalog edits.

## Storage and rollout

Implementation: `apps/backend/src/services/task-onboarding.ts`, with guidance in `task-onboarding-catalog.ts`. `TaskBoardColumn` and ordinary task contracts remain shared through `@aurboda/api-spec`. The app has one account-wide `task_board_settings` singleton; projects are filters, not separate boards. Thus there is no second board selection or per-project duplication. If no board exists, the shared routine creates the existing default workflow before appending the new column. Existing column order, task placement, completion and project associations are retained. A user-created column named Onboarding is left alone; the seed uses a fresh opaque column ID rather than title matching.

The durable per-account `task_onboarding_seed` singleton stores `id=1`, `catalog_key='optional-kanban-onboarding'`, the new `column_id` and `seeded_at`. It has no foreign key or deletion cascade to tasks or columns. It is independent of `user_settings`, `hidden_pages` and initial-guide progress. The catalog key is deliberately permanent across text edits and new-card additions: these changes apply to accounts not yet seeded, without refilling prior accounts.

`seedTaskOnboarding(UserDb)` runs in one transaction. It ensures/locks the singleton board row, checks the durable marker, appends one To do-category column, inserts every catalog card as a normal open projectless task, then writes the marker last. A failure rolls back content and marker together; retries and concurrent attempts serialize on the same row. No privileged client seeding route or shared mutable tasks are introduced.

Fresh account schema initialization calls the shared routine after table creation. Existing-account schema migration calls it before recording the schema fingerprint, and the normal migration entry point enumerates every provisioned account database: opening Tasks or logging in is not the rollout trigger. Accounts that never used Tasks or hide it are included by that migration sweep. Deployment/migration must finish successfully before claiming all accounts were seeded; this implementation is not a production deployment.

The regular board limit has one extra slot for the rollout, allowing a fully customized 20-column workflow plus Onboarding. The existing three workflow categories must still retain a column. No existing columns are discarded to make room.

## Manual completion, including existing work

Every account receives every card as an ordinary open task. The seeder does not inspect assessments, questionnaires, feature usage or other personal records to infer completion. Users who already did an action can move that card to their Done-category column or use its checkmark. This is part of learning to organize and maintain the board, not an automated completeness audit. No scores or saved feature records are changed, and there is no ongoing cross-feature auto-completion or recurring reassessment.

## Export, ownership and integration boundaries

The seeder receives the existing account's `UserDb`. Every new record remains in that private database with normal authentication, authorization and task mutation behavior. Task descriptions, board configuration and the durable marker follow the full per-user SQL export/restore and database-backup conventions; there is no allowlist to update. Source catalog text becomes ordinary stored task descriptions at seed time. An account export restores the marker too, so a restored deleted column is not refilled merely by opening Tasks.

See [account export coverage](ai/account-export.md) and [export/restore instructions](data-export.md). Shared Resources metadata/files live centrally and are outside per-account exports. Journal's private persisted entries/media follow their current storage/export contracts; local unsaved drafts and central data remain outside account downloads. No export is taken from a real account for onboarding verification.

Unmerged privacy PR #4 is an independent integration: do not promise its privacy controls, OAuth consent/revocation improvements or read-only scopes. The catalog describes the existing MCP read/write connection. Feature Control changes browser/web menus; the official upstream APK's native tabs/More hub do not yet consume these preferences. This fork does not distribute its own APK. No production deployment is included.

## Extending the catalog

Edit `apps/backend/src/services/task-onboarding-catalog.ts`. Preserve stable `key` values; keep a concise title and fuller ordinary task description with what/why/steps/link/done. Use actual interface labels, no deadlines or recurrent defaults, no administrator-only action. Put an approachable action before long assessments/integrations. `onboardingCatalog(columns)` resolves the first current In progress/Done-category titles; titles are initial guidance, not live cross-feature state.

Use normal Markdown links such as `[Mental assessments](/assessments)` to registered routes in `apps/web/src/index.tsx`. Task read views use the existing sanitized Markdown renderer; editing retains source Markdown. Navigation and hide/reveal labels come from `components/nav-links.ts`, the shared Feature Control registry. Every hideable destination needs Settings recovery instructions; never change `hidden_pages` to make a link visible.

Group assessment formats only when they are alternatives for one purpose. Distinct instruments/conditions/timings require separate guidance. Do not add queries or metadata to infer whether an individual completed the action; users manage completion themselves. Check version, units, accepted bounds, numeric projection, history and limitations against implementation and official/primary sources. Do not add questionnaires or promise unimplemented interpretation.

Run focused catalog/service/database/frontend checks and update this inventory. The catalog test covers the distinct mental assessment purposes and verifies all internal links are registered. A future catalog edit affects only accounts without the permanent seed marker. Deliberately distributing additional content to prior accounts requires a separate product decision and migration, never changing the marker key or deleting it to refill boards.

`task-onboarding-catalog.test.ts` covers stable actions, actual/fallback workflow titles, distinct mental assessment purposes, separate nutrition/treatment guidance, absence of recurring daily baseline cards, valid routes and hidden-page recovery. Persistence/concurrency/rollback/ownership and final handoff behavior are covered by their corresponding service, integration and frontend tests in this change. Final check results belong in the change report; historical feature documentation is not a claim that all suites or native builds passed for this revision.
