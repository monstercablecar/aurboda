## Runtime and boot order

The [workspace package](../../package.json) requires Node 26; [backend scripts](../../apps/backend/package.json) run TypeScript directly with `node src/api.ts`. Native `Temporal` is used by calendar and period code. Do not assume a compiled JavaScript backend directory is the runtime source. Docker/nginx routing and process setup are described in [Docker setup](../docker.md); the paths below are Express mount paths, which a reverse proxy may prefix externally.

`main` performs the following concrete stages:

1. Construct session, invitation and export-token helpers; initialize the central database; load deleted-user state; install usage recording; configure Sentry from server settings.
2. Construct integration clients, account services, synchronization, deduction/share callbacks and queues. A cluster client connected to `postgres` enumerates/provisions per-user databases. Some queues may remain unavailable; inspect each queue's initialization and fallback, not just whether HTTP started.
3. Mount CORS and the server's OAuth router. Mount stateless MCP before the global JSON parser, because it owns JSON-RPC parsing. Mount federation through `gateFederation` before that parser so signed inbox bodies remain under Fedify's control. Express trusts proxy headers only from loopback.
4. Mount the global 10 MB JSON parser, request audit and usage middleware, authentication/setup/sync/webhook routes, OwnTracks, and `mountRestRouters`.
5. Install Sentry's Express error handler, then the JSON error handler. Start listening, and run post-listen schema sweeps, selected backfills and account backfill. Listening is therefore not evidence that every background migration/backfill is finished.
6. On termination, use `createShutdownHandler` to stop timers/jobs, close HTTP and database pools, flush usage and exit. [process-guards.ts](../../apps/backend/src/services/process-guards.ts) handles failures outside request processing; initial startup failures before Sentry initialization may only reach stderr.

The JSON error handler returns an `HttpError` status or 500 and the exception message. Routes still need deliberate safe error messages: this handler does not automatically remove sensitive details.

## Authentication and protocol boundaries

**Session tokens are not JWTs.** `createAuth` encrypts the username with AES-256-GCM using a required 32-byte session secret, random IV and authentication tag. The payload contains no expiration timestamp. `loginToUserDb` checks credentials through an actual PostgreSQL connection as the user's role; a warm service pool is not accepted as a password check. Signup validates usernames and provisions the user's database. Passkey endpoints are wired through [webauthn-router.ts](../../apps/backend/src/routes/webauthn-router.ts).

REST `createAuthMiddleware` decodes the token into `req.user`, rejects users in the deleted-user cache, performs the per-process schema check and applies the account write gate. Restricted writes receive 402; allowed reads and exceptions come from [read-only.ts](../../packages/api-spec/src/read-only.ts). Admin routes additionally query central admin status. Ordinary services receive the authenticated username, never an arbitrary request-body owner.

MCP differs deliberately: `createMcpRouter` accepts OAuth access tokens via [oauth.ts](../../apps/backend/src/services/oauth.ts), or the encrypted session token. It creates a fresh server/transport for each POST, parses up to 4 MB, trims tool-call arguments and closes the server after handling the request. GET/SSE and DELETE/session management return 405. Tool registration binds the authenticated user into callbacks. Tool-list summaries are abbreviated; `describe_tools` returns full nested schemas. MCP does not run the REST middleware chain: shared services must enforce invariants independently.

Read-only MCP enforcement depends on tool names: [usage-channel.ts](../../apps/backend/src/services/usage-channel.ts) classifies known mutation prefixes; [read-only-gate.ts](../../apps/backend/src/mcp/read-only-gate.ts) replaces disallowed callbacks. New mutating tools must use a recognized prefix or extend that classifier. This is not inferred from a tool's implementation.

Domain services should validate invariants again where REST and MCP take different paths. Serialize database `Date` values at the boundary.

## Database ownership and schema lifecycle

Each username selects `aurboda_<username>`. `getDbForUser` caches a promise for a bounded pool (maximum five connections). Physical connections authenticate with the service credentials and run `SET ROLE` to the user's role before first use. Failed role assignment destroys the connection. A `withUserTransaction` callback must use its supplied `tx` for **every** statement; querying by username from inside it would use a different connection.

The central database contains server configuration, admins, account/plan/usage information, deleted usernames, OAuth clients/codes/tokens, passkey handles, provider-user mappings and shared catalog/import data. It is not the owner database for arbitrary health/People records. `central-db.ts` delegates much of this to `central-*` modules. The pg-boss store defaults to the shared database but its configuration can select another database; it uses its own `pgboss` schema and bounded pool.

New-user provisioning creates the role/database and required extensions before `initializeSchema` executes registered DDL in dependency order. The schema registry is explicit: adding a file under `schema/` does not register it. For a truly empty database, initialization records the current fingerprint. Existing databases run `migrateSchema`, including column/data transformations and DDL creation. The fingerprint hashes ordered statements plus `MIGRATION_REVISION`; non-DDL migration changes need a revision change to trigger upgrades. [migrate.ts](../../apps/backend/src/migrate.ts) is a separate legacy-data import script, not the normal incremental migration runner.

There are three upgrade paths: post-listen `migrateAllUsers`; the first authenticated REST request's cached `migrateSchemaIfNeeded`; and `query(user, ...)` retry after recognized schema errors (undefined table/column or not-null violation). A failed first-request schema check now returns 503, evicts its failed promise and allows retry; it does not continue into the route. Transaction calls through a `Queryable` do not use the username-based repair branch. Migration routines are substantial and are not one global transaction; inspect each transformation before altering it.

Core storage remains domain-specific: `raw_records`, `time_series`, activities, spatial data, productivity, meals, reports, social and system tables. [Data storage](../data-storage.md) describes the primary model. “Raw preservation” is an ingestion pattern, not a guarantee that every manual domain write is duplicated in `raw_records`; People writes its own normalized ownership tables and JSONB payloads.

## Ingestion, derived data and jobs

A concrete Android path is `mountSyncRouter` → `createSyncRouter` → `processHealthConnectData` / `processHealthConnectBatch` in [db/health-connect.ts](../../apps/backend/src/db/health-connect.ts). These preserve raw source records and extract supported time-series/activity data. Source arrivals can enqueue enrichment through [source-enrich-queue.ts](../../apps/backend/src/services/source-enrich-queue.ts). Provider details/GPS tracks can enter [track-queues.ts](../../apps/backend/src/services/track-queues.ts).

Pull clients and transforms live under [integrations/](../../apps/backend/src/integrations/). [sync-provider.ts](../../apps/backend/src/services/sync-provider.ts) implements shared “if needed” synchronization with per-user/method in-flight coalescing and recheck suppression. [sync-scheduler.ts](../../apps/backend/src/services/sync-scheduler.ts) invokes that same provider on a five-minute schedule, respecting stored provider intervals. Explicit `/sync` wiring lives in `sync-setup.ts`; webhook callbacks live in `webhooks-setup.ts`. Imported ICS calendars use [integrations/ical/sync.ts](../../apps/backend/src/integrations/ical/sync.ts): `parseICalEvents` / `syncCalendar`, which persist `calendar_event` activities plus raw records; this is separate from People date projections. The parser does not expand recurrence rules, so importing a recurring series is not equivalent to materializing every occurrence. See [calendars](../calendars.md) for supported behavior.

`api.ts`'s `activityNotifier` sends a mutation window to deduction and autoshare queues. [deduction-queue.ts](../../apps/backend/src/services/deduction-queue.ts) groups/evaluates relevant rules; [autoshare-queue.ts](../../apps/backend/src/services/autoshare-queue.ts) handles sharing rules after their stabilization delay. New ingestion or activity-mutation paths must preserve these callbacks, or derived activities/shares can lag despite successful persistence. These notifications are fire-and-forget queue triggers, not a single database transaction with the source write.

People reminders reuse pg-boss rather than another scheduler. `createPeopleReminderScheduler` sweeps every minute. [db/people-reminders.ts](../../apps/backend/src/db/people-reminders.ts) locks the parent/event with `FOR UPDATE SKIP LOCKED` and records delivery state by event/revision, including retry timing. [browser-push.ts](../../apps/backend/src/services/browser-push.ts) validates stored subscriptions and sends generic private wording; notification text does not contain the person's name or notes. Availability requires the scheduler and VAPID configuration; browser permission/subscription and provider acceptance are separate delivery constraints. Provider acceptance is not proof the user saw the notification. See the reminder guide for retry and crash-window limitations.

## Sharing and People privacy boundaries

Public shares intentionally select an owner's database from a validated public username. They do not use `req.user`; authorization instead depends on published share records and visibility checks. `resolveDashboardData` accepts stored widget configuration, calls owner-scoped services and returns widget-specific data rather than arbitrary raw query results. `private`, `unlisted` and `public` are distinct; unlisted is not private. Federation, public images and HTML/OpenGraph pages have their own guarded mounts. Preserve these boundaries when extending widgets or shareable data.

People uses [schema/people.ts](../../apps/backend/src/schema/people.ts) and [db/people.ts](../../apps/backend/src/db/people.ts): person UUID, cascading events/feedback/reminder deliveries, and private metric points. It deliberately does **not** publish these points into the generally selectable native custom-metric/time-series registry. Journal/memory text is not analyzed or projected into counts. Goals are event records with statuses/target dates; enabling the Goals metric only enables a counter, not goal creation or progress inference.

`getPeopleCalendar` validates an inclusive date range, loads only the current user's people/timezone, and calls [people-calendar.ts](../../apps/backend/src/services/people-calendar.ts): `buildPeopleCalendar`. `/people/calendar` is authenticated JSON, **not a public ICS subscription feed**. It creates no generic tags or external calendar events. Birthday deduplication, date kinds, leap-day recurrence and optional ideas are deterministic. [people-dates.ts](../../apps/backend/src/services/people-dates.ts) produces the profile's next-occurrence display. Existing age calculations use UTC; important-date day boundaries use the account timezone with UTC fallback.

Google support is a browser-side individual copy link, [googleCalendar.ts](../../apps/web/src/pages/People/googleCalendar.ts): `peopleGoogleCalendarHref`. It opens Google's event editor for the selected occurrence; the user reviews/saves it and configures recurrence there. There is no Google write API, token-backed synchronization, or propagation of later People edits to that copy in this implementation.

“Private to the owner” is not a complete log-erasure guarantee. New automatic REST audit entries retain only structural metadata; historical audits and other logging paths remain independent. See [privacy hardening](privacy-hardening.md).

## Recent People flows: preserve their separate meanings

The shared contract remains [schemas/people.ts](../../packages/api-spec/src/schemas/people.ts), and both REST and MCP call [services/people.ts](../../apps/backend/src/services/people.ts). No separate care database or rules engine was introduced.

- **Profile/status mutation:** `updatePerson` locks the owner-scoped person, merges parsed PATCH fields, then calls `validateStatusEpisodes`. Every existing episode must remain in the array; archive instead of removal. A stale array omitting a newly added episode is rejected. Kind is immutable, transitions are server-owned, and omitted fields do not reset preferences. This prevents missing-episode loss but is not a general field-level optimistic concurrency protocol.
- **Observation mutation:** `createEvent`/`updateEvent` validate episode ownership, metric/milestone definition and consent/source rules before persisting the existing JSONB event. Supplied payload is a replacement; omitted payload preserves it. Existing history remains editable after agreement withdrawal/resolution, while new sensitive collection is gated. Private points rebuild from events; journals/memories do not produce inferred care metrics.
- **Dashboard read:** one `now` drives `peopleContext`, matching and metric windows. [people-status.ts](../../apps/backend/src/services/people-status.ts) uses the account calendar date for episode duration/gestation; the established developmental context still uses UTC. Resolved dating freezes when a resolution date is supplied. Unknown gestation produces `timing_unknown` milestones, not a fabricated appointment date. Estimated due dates never create a birth, postpartum episode, reminder or outcome.
- **Advice and Help Tree:** `matchGuidance` extends the existing pipeline with all/any/exclude and same-episode timing/phase predicates, safety-first deduplication and explicit nonclinical support-log conditions. `evaluatePeopleGuidance` uses that same pipeline. `GET /people/help-tree` / `get_people_help_tree` return actual catalog dependencies; optional person evaluation loads only the authenticated owner's profile. UI browsing filters are not a second eligibility engine.
- **Metrics:** legacy IDs remain intact. New rolling IDs use `recorded:` to avoid collisions with old arbitrary units. Care IDs include episode UUIDs. A resolved episode's metrics require both explicit retention and existing enabled IDs; history stays visible independently. Neither mood ratings nor counts are relationship scores, diagnosis thresholds or inferred progress.

See [People care](../people-care.md) for complete contracts and extension scenarios. Catalog review metadata records checked claims and agent scenario-based empathy review, not independent clinical approval.

## Extension checklist grounded in existing patterns

1. Define shared Zod fields/types in `api-spec`, export them, and regenerate OpenAPI/client models. For PATCH schemas, remove creation defaults from optional fields; omitted fields must not reset stored preferences. People schemas demonstrate this explicitly.
2. Put ownership and business invariants in `services/`; invoke the same service from typed REST handlers and MCP tools. Do not rely on REST-only validation for an invariant required by MCP.
3. Add domain SQL to the schema registry/dependency order and provide an upgrade path for existing tables. Use owner-scoped queries and same-connection transactions; test distinct user databases and delete cascades.
4. Register REST in the correct composition module and MCP in `createMcpServer`. Maintain mutation naming/read-only classification. Put static routes before wildcard identifiers.
5. For ingestion, preserve source identity, corrections/deletions and downstream notifier/queue hooks. For shares, explicitly design the public projection; never reuse a private payload wholesale.
6. Test schemas/rules as units, REST/MCP boundary behavior and real database isolation/lifecycle separately. [vitest.config.ts](../../apps/backend/vitest.config.ts) separates integration tests; [db-test-helper.ts](../../apps/backend/src/test/db-test-helper.ts) provisions isolated databases through the integration setup. A testcontainers/Podman failure is not evidence that a domain assertion passed or failed.

## Relationship-state history

`services/people.ts` records relationship-state set changes during profile create/PATCH in the same `peopleTransaction` as the profile write. `services/people-relationship-history.ts` creates start/end transitions, pairing an end with the latest tracked start; an existing selection without a recorded start stays unknown. `db/people.ts` stores these private records in the existing `people_events` table. There is no migration or backfill.

The shared `PeopleEvent` read contract accepts `type: relationship_state`, `source: system` and relationship-state payload fields; manual create/PATCH event contracts do not. Shared service guards reject editing/deleting automatic records, so REST and MCP behave alike. Profile deletion still deletes its owned history. Metrics exclude these transitions. Dashboard recent history and the full events endpoint return them; the web renders them read-only. Dates mean when a selection was saved, not a retrospectively established date in the relationship. See [marriage state workflow](../people-marriage.md).
