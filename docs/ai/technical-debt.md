## Deliberate limitations, not hidden completed features

- **Session lifetime:** `apps/backend/src/auth.ts` encrypts a username with AES-256-GCM; session tokens are not JWTs and carry no expiry. Document deliberate lifetime/revocation policy before changing clients. Deleted-user rejection and encryption-key rotation are separate controls.
- **MCP mutation classification:** `apps/backend/src/services/usage-channel.ts:64` uses recognized name prefixes for read-only enforcement. Registering a differently named mutation requires updating classification or adopting explicit mutability metadata; current People feedback uses `set_person_guidance_feedback`.
- **People privacy:** `people_metric_points` is private and not the generic `time_series` sharing path. Reusing global custom metrics would require an explicit privacy design. New automatic request audits are minimized; historical retention and other logging paths remain separate boundaries.
- **Distinct goal concepts:** global metric goals, Work goals/configuration, and People timestamped goal events serve different purposes; profile `goals` strings are guidance preferences. No cross-system goal synchronization is implemented. Use clear names before attempting consolidation.
- **Dates and notifications:** People dates appear in Timeline. They do not automatically schedule reminders. Event reminders require the pg-boss scheduler, push configuration and a browser subscription (`services/people-reminders.ts`, `services/browser-push.ts`).
- **Google Calendar:** the button opens one occurrence for review/save; users set any yearly repeat in Google. It does not update/delete an existing Google event after a People edit and does not subscribe Google to a private feed.
- **Calendar imports:** existing ICS ingestion and People calendar projection are distinct sources. The People endpoint is authenticated JSON, not an externally subscribable ICS URL.
- **Evidence catalog:** People recommendations are local, versioned records and deterministic matching. Optional gender adds supported context, not inferred anatomy or diagnoses. Catalog gaps and source review needs are recorded in [coverage](../people-catalog-coverage.md).
- **Theme:** People primary buttons now use the documented primary token for white text; custom themes still need their own contrast review.
- **Work draft code:** `apps/configurable-work-engine/src/schema/work.ts` and archived `docs/experiments/work-schema.ts.txt` are disconnected drafts. In contrast, `packages/api-spec/src/schemas/work.ts` is actively exported and used by Work settings; its valid contracts do not establish a separate Work-specific REST/storage engine. See [feature status](frontend-and-features.md).

## Suggested work order

1. Review remaining logging/retention boundaries before proposing historical deletion; erasing primary records does not erase backups or audit history.
2. Preserve transaction and session-isolation regression tests when changing Work or authentication.
3. Clarify future questionnaire ownership and external calendar synchronization contracts before broadening those systems.
4. Benchmark People histories and web chunks before optimizing; retain correctness for goals, corrections and deletion.
5. Keep native SDK/JDK verification and source-manifest release evidence separate from web checks.
