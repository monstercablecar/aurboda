# Request-audit privacy and schema-check failures

This scoped change hardens automatic REST request auditing and the authentication middleware's schema-check gate. It does not purge historical audit data or change application records. The source files are [audit-body.ts](../../apps/backend/src/api/audit-body.ts), [middleware.ts](../../apps/backend/src/api/middleware.ts) and their adjacent tests.

## Body summaries

`summarizeAuditBody` emits only fixed structural metadata:

| Input        | Retained metadata                              |
| ------------ | ---------------------------------------------- |
| Missing body | No body summary                                |
| Null         | `body_type: null` (the type label is a string) |
| Array        | `body_type: array`, top-level `item_count`     |
| Object       | `body_type: object`, top-level `field_count`   |
| Scalar       | Its type label, never its value                |

No caller-controlled key names, string fragments, booleans, numeric answers, nested objects or array elements are copied into the summary. The same policy applies to small and large bodies, credentials, profile notes, questionnaire answers and error echoes. The implementation never serializes a body or recursively visits its values. Object summarization enumerates only top-level keys to count them; arrays use their length. This avoids recursion depth/cycle hazards and does not invoke property getters or `toJSON` for ordinary objects.

`createAuditLogMiddleware` applies the summary to authenticated write requests and captured JSON error responses. Scalar JSON error responses are summarized rather than retained verbatim. Existing audit attribution, operation method/static route template, severity and persistence timestamps remain in place; server-selected HTTP error status remains operational metadata. Responses sent to the client are unchanged. The middleware still skips read-only HTTP methods and deleted users according to its existing rules.

This is deliberately less diagnostic detail than the old whole-small-body policy. Do not add an arbitrary per-field exception for convenience: a field name can itself contain private data, and ostensibly operational fields in a request can be controlled by the caller. Any future retained value needs a narrowly defined server-owned source and privacy review.

## Remaining privacy boundaries

This policy changes new entries generated by this middleware. Existing audit rows, backups, exported logs and previously collected telemetry are **not** deleted or rewritten. Primary-record/person deletion does not imply erasure of those independent stores. The existing targeted Garmin audit-redaction backfill remains separate and is not a general historical purge.

The follow-up also hardens `validation.ts` (static route and issue count), the global `api.ts` error audit (static route, HTTP status and coarse error type), and five downstream-error audit calls in `services/mutations.ts` (coarse error type). Other direct audit callers, console logs, provider logging and telemetry are outside this reviewed scope. Audit operations now use the resolved static route template or the fixed label `unmatched route`; raw paths, query strings and parameter values are not retained by this middleware. Do not generalize this patch into a claim that every log is free of personal data. Retention, broader logging review and any consented historical cleanup need their own scope and verification.

## Schema-check gate

`createAuthMiddleware` caches one schema-check promise per authenticated user per middleware instance. Concurrent requests await the same in-flight check. Only a successful check remains cached; it then starts the existing background backfills.

A failed check now rejects waiting requests with HTTP 503 and a generic retry message. The underlying database error is not reflected in that message, the protected route does not run, and the failed promise is evicted so a later request can retry. Invalid/deleted authentication still follows the separate unauthorized path. Successful checks retain their existing once-per-instance behavior; background backfill failures retain their separate handling and do not turn a successful schema check into an authentication failure.

The change does not make migrations globally transactional or alter the post-listen migration sweep, query-level schema repair, MCP authentication path, or the account gate's separate failure policy. Its guarantee is specifically that this REST authentication middleware does not continue after its own failed schema check.

## Verification

Focused tests cover deep/cyclic payloads, nested credentials and health data, dynamic malicious keys, large arrays/strings, success/error audit entries, scalar error echoes, rejected concurrent migration checks, later successful retry and success caching. The initial two-file suite passed 25 tests; expanded coverage across four files passed 131 tests; backend typechecking also passed after the separate Work-draft quarantine. See the current source/tests rather than treating this record as a future checkout's verification result. No live user records, historical audits or backups were inspected or modified.
