## Deliberate compatibility choices

Upstream's separate `people(name, actor, deleted_at, …)` table, notes-based Journal repository, alternate reminders/push subscription tables and service worker are not installed over canonical fork storage. Upstream People actor sharing, person-name public correlations and automatic People/Journal purge jobs are not enabled. Private time-with analysis is implemented explicitly above; preserving private defaults does not remove it. Generic opt-in outputs remain useful general metrics/activities, while treatment administration facts are not reclassified as generic answers.

Old application readers accept representative new records using additive schema: new check-in-owned manual metrics/activities, new notification type, dashboard card settings and Journal activity-link kind. An old image cannot expose or edit newly introduced UI; rollback preserves that data for a later upgrade. No application downgrade reverses DDL.

## Preservation and rollback acceptance

`services/rollback-compatibility.integration.test.ts` runs the actual previous immutable image (`localhost/foghouse-aurboda:treatment-checkins-96a9916f-20261118`) against a disposable migrated schema and representative new data. Its second test installs the previous image's exact DDL, seeds rich People/workbook/revision/attachment/treatment/reminder fixtures, applies current migration twice and compares the original rows exactly before current application reads.

`services/export-dump.integration.test.ts` dumps and restores into another disposable database, compares saved tables including new forms/responses/retry/output-ownership/With records, and reads the restored Journal, private links and response data through application services. Existing profile/workbook/attachment bytes and factual treatment history are included.

Local integration runs set `AURBODA_TEST_FAST_DISK=1` only on disposable PostgreSQL: fsync and synchronous_commit are off to keep the large suite practical on this workstation. These tests exercise SQL transaction rollback, fault injection, concurrency and restore fidelity; they make no power-loss/crash-durability claim. Production database durability/configuration is never changed.

## Password normalization review correction

Final Astra review found one blocker: the new verifier used NFKC alone while pg mapped non-ASCII spaces and mapped-to-nothing characters first. A soft hyphen could therefore make a newly created or reset password reject its original input. The verifier and pg client now share one helper via a hash-pinned `pg@8.23.1` pnpm patch. Docker copies the patch before both frozen installs, and Node/Docker change detection includes patch files.

The helper follows the deployed PostgreSQL 16 algorithm and exact Unicode 3.2 range tables from [PostgreSQL source 30d95d73](https://github.com/postgres/postgres/blob/30d95d7318e79e1816065f75cbe7f1d31d427f97/src/common/saslprep.c), retaining its copyright and permission notice. It preserves ASCII behavior, maps spaces/removals, applies mapped-input prohibited/unassigned/bidi checks, and falls back to the original UTF-8 password when required. This check order matters: characters unassigned in Unicode 3.2 must not become accepted merely because a modern NFKC implementation can transform them. Existing PostgreSQL-generated credentials remain readable. This adapter targets the pinned PostgreSQL 16 deployment; reassess it against the server oracle when upgrading the database or pg rather than silently dropping the patch.

All 66 focused SCRAM/connection/account-email tests pass. Sixteen cases exercise actual role creation/reset → login, compare local verifiers to PostgreSQL's own verifier using the server's salt, and authenticate existing server-generated credentials. Cases include soft hyphen, joiners/selectors, non-ASCII spaces, composed/compatibility/supplementary normalization, Unicode 3.2 unassigned input, empty mappings, prohibited/private-use input and valid/invalid bidi. Clear passwords are sent in SQL only for the synthetic disposable test oracle; production CREATE/ALTER still send verifiers.

Astra's bounded final review found no other blockers in its scope. This correction and dependency patch were applied afterward; no claim is made that Astra re-reviewed the corrected head. Both automatic specialist consultations are used. The required current-head GitHub review must cover the correction before merge/deployment.
